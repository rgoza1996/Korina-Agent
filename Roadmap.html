Future follow-up: Agent visibility

Status: ready

Recommendation: pause new Korina Converse feature work temporarily and give Korina Agent one focused visibility and reliability sprint. Converse remains in bugfix/dogfood mode for audio, provider, and blocker regressions.

Why now: Agent is the next differentiating surface: hidden state, transcript awareness, background observations, interruption recovery, and later DAG memory all depend on an event loop that is observable before it is clever. If Agent is quiet or ambiguous, later behavior work becomes hard to debug and easy to misread.

Plan

StepScopeExit condition
1 — Runtime gateVerify Agent enable/disable behavior through the supported config/API path.The UI and server agree on whether Agent is enabled, and the disabled state fails quiet by design.
2 — Debug panel dogfoodExercise transcript delivery, event polling, busy/idle state, cooldown/deferred-interrupt reporting, and browser-console health during a real conversation.The Agent Debug panel explains what just happened without requiring log spelunking.
3 — Regression coverageAdd backend route tests for transcript/events, frontend static tests for the debug element and imports, and a smoke check for stable event response shape.A broken Agent panel or event loop fails CI before reaching the live page.
4 — Debug state expansionSurface last transcript delivery, last event id, busy/idle, last error, and cooldown/deferred-interrupt state.Agent behavior is inspectable enough to support the next behavior feature without guessing.
5 — First behavior sliceOnly after visibility is green, add a small observation/event-memory slice that records what Agent saw rather than changing conversation behavior.The first Agent feature produces durable observations while remaining reversible and low-risk.

Ordering rule: do not start new Agent behavior until steps 1–4 are green. New Converse features stay paused during this sprint; critical Converse bugfixes remain allowed.

Duplex Workflows (Wan-Streamer Lessons)

Status: parked

Unblock condition: A reviewed hackathon release and recorded voice rehearsal are complete. The existing first release line on master is not evidence for these proposed duplex features.

Source paper: Wan-Streamer v0.1: End-to-end Real-time Interactive Foundation Models (arXiv:2606.25041v2). Wan-Streamer is a model; Korina is a harness. The lesson is to enforce a system-level streaming contract at the harness layer.

What Wan-Streamer teaches

  • Streamability is a constraint, not a serving optimization. A system designed around offline encoders or round-based dialogue cannot recover true low-latency full-duplex behavior by engineering alone.
  • Full-duplex is not alternating turns. While the agent responds, it must still perceive user feedback for interruption and adaptation.
  • Commit generated units back into history. If a reply is interrupted, what was actually spoken is what context should anchor on — not what the model intended to say.
  • Overlap independent work (thinker/performer): current STT processes while prior TTS plays; LLM streams while Kokoro synthesizes the first sentence.
  • Measure the right latency boundary. Model-internal, first-packet, first-token, endpointing, and API TTFB are useful but not equivalent to user-perceived latency. Korina needs signal-to-signal timing in its debug strip.

What Korina would adapt

PhaseScopeWhy now
0 — TelemetryLatency event schema, /api/duplex/events, browser recorder helperRequired for every later phase. Cannot optimize what is not measured.
1 — Streaming TimelineSingle harness-level event log shared by STT, LLM, TTS, playback, and interruptsThe "interleaved causal stream" in harness clothing.
2 — Barge-InTrack active audio nodes, keep VAD on while TTS speaks, stop TTS within ~250 ms on detected speech, recover with contextBiggest visible duplex win. Token-efficient on the existing UI.
3 — Streaming LLM → Sentence TTSOpenAI-compatible stream: true, sentence chunker, speak first clause before LLM finishesEliminates dead air between LLM and TTS.
4 — Stable Partial STT PrefillBehind a feature flag; do not speak from partial-only input yetRisk: hallucination. Slower adoption is correct.
5 — Duplex SchedulerPriority model: barge-in > user audio > STT final > LLM token > TTS synth > playback > background agent; write a small scheduler design doc before implementation.Encodes Wan-Streamer's "multimodal token scheduling" at harness level and guards against talk-over/starvation failures.
6 — Latency Budget UISurface full signal-to-signal path in debug strip; dogfood protocolMakes the work visible during beta and regressable in CI.
7 — Presence HooksDisability-friendly state events for future avatar or status-light consumersWan-Streamer highlights visible listening behavior. Audio-only Korina can still expose the state.
8 — Session Duplex StateServer mirror of spoken prefixes so reconnects do not erase context; store the actually spoken prefix, not the full intended reply.Required for reliable interrupt recovery on flaky networks. Depends on Duplex telemetry/streaming timeline plus DAG Memory Phase 1 so the spoken prefix can live as an observation node.

Interrupt-recovery note: once Duplex telemetry/streaming timeline and DAG Memory Phase 1 are live, interrupted speech should be committed as an observation node containing the actually spoken prefix. Session Duplex State should read from that memory substrate instead of inventing a parallel prefix store.

DAG Memory System (Post-v2)

Status: parked

Target release: Korina Converse release 2 or 3.

Source spec: Korina Memory.txt (engineering spec, v1.0, 782 lines). 782-line engineering spec, v1.0. Will move into the repo as docs/specs/korina-memory-v1.md when implementation starts.

What it is

A causal DAG of event nodes (assertions, observations, tool calls, inferences, hypotheses, invalidations) connected by hard and soft edges, with built-in truth retraction, hypothesis generation for conflicts, and a confidence decay model. It is the substrate Korina Agent uses to remember what it has seen, decided, and been told — without losing information to context-window compression.

Core concepts

ConceptRole
EventNodeAtomic record: type, content, key, value, base_confidence, depth, timestamp, session_id. Never mutated after creation.
Hard edgeSystem-generated, immutable. Only three kinds: tool_call→observation (depends_on), observation→assertion (invalidates, on key mismatch), tool_call→tool_call (sequential depends_on).
Soft edgeLLM-proposed with lifecycle (proposed → evaluated → committed / rejected / expired). Has TTL anchored to runtime context: job boundary in Hermes, turn count in Converse, task boundary in Agent.
InvalidationA new observation whose value differs from an existing assertion under the same key auto-invalidates the old assertion and propagates through dependent nodes. Observations are never invalidated themselves.
HypothesisWhen two valid observations disagree on the same key, the system generates 2–4 competing hypothesis nodes (real EventNodes, not inline notes) with base_confidence 0.2 and waits for supporting observation.
ConfidenceC(node) = geometric_mean(C(parents)) × exp(−λ × depth) with λ = 0.08. Observations are always 1.0. Retrieval prunes below threshold 0.3.

Build order (do not reorder)

PhaseComponentDepends on
1DAG store + hard edge traversalnone
2Invalidation enginephase 1
3Retrieval (hard edges only, no confidence)phase 2
4Structural conflict detectionphase 3
5Hypothesis generationphase 4
6Soft edge state machine + TTLphase 3
7Confidence model + threshold pruningphases 3, 6
8M3 integration hooksphases 3–7

Phases 1–3 are the core correctness system. Phases 4–7 are incremental improvements that degrade gracefully if absent. Phase 8 is offline-only and never blocks runtime.

Why this lives on the Roadmap, not in active work

The hackathon release has to pass its own demo gate before expanding into new infrastructure. The DAG memory system is significant new infrastructure — it adds a SQL store, an invalidation engine, hypothesis-generation LLM calls, and a confidence cache that must all be correct before any benefit is real. Wrong implementations are worse than no memory: silent confidence drift, stale assertions surfacing as facts, hypotheses leaking into context as conclusions. That is exactly the failure mode the spec is designed to prevent, and it is exactly the failure mode shipping too early invites.

Releases 2 and 3 are the right place. By then Korina Converse will have live sessions producing real events, so phases 1–3 can be designed against actual data shapes instead of guesses, and the confidence model has real signals to calibrate against (lambda is a tunable that should not be locked in at 0.08 before live data exists).

Why this is parked

A verified voice demo and clear runtime boundaries are the gating event for this sprint. These proposals should be revisited after that evidence is available. The full plan lives in the repo at docs/plans/korina-converse-duplex-post-v1.md and is rendered on this page so it stays discoverable.

Note: Roadmap items are proposals, not commitments. Scope, ordering, and even the inclusion of an item can change as the v1 release and post-v1 feedback arrive. The Wan-Streamer plan in particular is a starting point for discussion — the duplex rollout will likely be split across multiple post-v1 milestones, not one big push.
